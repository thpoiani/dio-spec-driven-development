Definição de Spec

Spec é contrato, não documento

"Um contrato de como o código deve se comportar — e a fonte da verdade que ferramentas e agentes usam para gerar, testar e validar código"

Não é um documento estático: artefato vivo e executável — GitHub Blog

01

Requisitos e critérios de aceitação

O comportamento esperado, com cenários verificáveis.

02

Constraints e edge cases

Limites, exceções e o que está fora do escopo.

03

A linguagem do domínio

Os termos que o código, o teste e a conversa compartilham.

Definição do GitHub Blog; o que entra na spec vem do Microsoft Dev Blog (guardrails, requisitos, constraints, acceptance criteria, edge cases). Enfatize "fonte da verdade": quando código e spec divergem, a spec vence.

Concreto

O que uma spec diz que um prompt não diz

spec.md 
### Requirement: Total nunca negativo
O sistema **DEVE** limitar o total a zero quando o
desconto exceder o subtotal.

#### Scenario: Desconto maior que o subtotal
- **QUANDO** o subtotal é 3000 centavos e o cupom
  fixo é de 5000 centavos
- **ENTÃO** o desconto é 5000 centavos e o total é 0
Leia o trecho em voz alta — é pequeno e vale a leitura. Nenhuma dúvida resta sobre o que acontece quando o desconto estoura o subtotal.

O ciclo que substitui o chute

O ciclo se repete por mudança, não por projeto: cada nova feature entra pelo topo, não do zero.

Fowler · Böckeler

SDD não é uma coisa só: três níveis

Cada nível herda o anterior — e se compromete mais com a spec.

01

spec-first

A spec nasce antes do código e orienta a tarefa.

02

spec-anchored

A spec sobrevive à tarefa e evolui com a feature.

03

spec-as-source

Só a spec é editada; o código é gerado dela.

Fonte: Birgitta Böckeler no Martin Fowler (out/2025) — "SDD ainda está em fluxo; todo SDD é spec-first, nem todo um é spec-anchored".

prompt

modelo: GLM-5.3-Flash

  • Prompt idêntico, mesmo Agent e mesmo modelo em todas as execuções.

O que cada método faz com o que não sabe

A ausência de regras não tem o mesmo peso

  • Baseline: invenção silênciosa — cupom expirado funciona para sempre.
  • GitHub Spec Kit: Assumptions — o "fora do escopo" declarado no documento.
  • OpenSpec: Non-Goals — lista própria no design.
  • Matt Pocock's Skills: Out of Scope + GLOSSARY.md que nomeia o que falta.
A spec fundida em openspec/specs/ sobrevive à change — é o que separa spec-first de spec-anchored na prática.

O que muda quando existe spec

Só o prompt

O agente inventa o que faltou, erra em silêncio — o bug chega em produção — e não deixa nada para a próxima sessão.

Menos retrabalho

Ambiguidade resolvida antes: a IA gera contexto estruturado.

Alinhamento total

Produto, engenharia e teste na mesma fonte de verdade.

Entrega previsível

Validação amarrada à intenção original; mudar de rumo é atualizar a spec e re-gerar.

Menos surpresas

O agente sabe o quê, o como e em que ordem — menos chute, menos surpresa.

Validação de graça

Os critérios de aceitação viram testes — a verificação nasce junto com o código.

O artefato sobrevive à sessão

Outra sessão, outro agente ou outro operador continuam do contrato — sem re-explicar nada.

Destilado do Microsoft Dev Blog e do GitHub Blog: menos retrabalho e surpresa; alinhamento entre produto, engenharia e teste; entrega previsível; e a validação nasce junto — os critérios viram testes. E o achado do nosso estudo: o processo nunca erra em silêncio. Caso real: onboarding em brownfield caiu de 2–3 semanas para dias.

Recapitulando

  • Spec é contrato e fonte da verdade — não documento que se arquiva.
  • O que você não diz, o Agent inventa — importância de harness, com coding standards and patterns, constraints and guardrails.
  • A spec orienta como gerar, testar e validar — o ciclo nunca termina nela.
  • Quanto melhor a qualidade de um Spec, mais eficiente o processo de desenvolvimento.
Recap não é resumo: é a versão curta que a pessoa repete no elevador.
